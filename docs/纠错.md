## 1. styling.py — 两个方法缺 `self` 参数

### 现象
日志格式异常，context 显示原始英文 dict 而非中文标签，如：

```
改前：[适配器回调] 收到消息 | {'self_id': 1972693082, 'user_id': 3892328896, ...}
改后：[适配器回调] 收到消息 | 机器人ID: 用户****3082 | 用户ID: 用户****4908 | ...
```

### 根因
`style/styling.py` 中 `StylingManager` 类有两个实例方法定义缺少 `self` 参数，导致调用时 TypeError，`format_context_to_chinese` 异常回退到 `str(context)`。

### 修改内容

| 方法 | 改前 | 改后 |
|------|------|------|
| `format_dict_message` | `def format_dict_message(json_data)` | `def format_dict_message(self, json_data)` |
| `replace_message_keywords` | `def replace_message_keywords(message)` | `def replace_message_keywords(self, message)` |

### 为什么之前没触发
这两个 bug 从初始提交 `778dba6` 就存在。旧的消息处理路径（`dispatch_plugin_cmd`）不调用 `log_with_context(context=...)`，不会走进 `format_context_to_chinese`，因此从未暴露。新版 Pipeline 的 `SecurityFilter._log_via_styling` 首次触发了这条路径。

## 2. OneBot 适配器 — HTTP 模式误启 WebSocket 服务

### 现象
配置文件 `type: http`，但日志显示 OneBotWS reverse 模式已启动 0.0.0.0:8080。

### 根因
`OneBotAdapter.__init__` 中 `ws_mode` 默认值为 `"reverse"`，且 `start()` 无条件调用 `self._ws.start()`，导致 HTTP 模式下也启动了无效的 WS 监听。

### 修改内容

#### `core/gracy_adapter/onebot/adapter.py`

| 位置 | 改前 | 改后 |
|------|------|------|
| `__init__` 默认参数 | `ws_mode="reverse"` | `ws_mode=""`（空=不启动WS） |
| `__init__` WS 创建 | 无条件创建 `GracyOneBotWS` | `_ws_enabled=bool(ws_mode)`，有条件创建 |
| `start()` | `self._ws.start(on_event)` 无条件 | `if self._ws_enabled: self._ws.start(on_event)` |
| `stop()` | `self._ws.stop()` 无条件 | `if self._ws_enabled: self._ws.stop()` |
| `send()` | `if self._ws._ws is not None` | `if self._ws_enabled and self._ws._ws is not None` |
| `call_api()` | `if self._ws._ws is not None` | `if self._ws_enabled and self._ws._ws is not None` |
| `get_platform_info()` | `if self._ws._ws is not None` | `if self._ws_enabled and self._ws._ws is not None` |
| `is_ws_connected()` | `return self._ws._ws is not None` | `return self._ws_enabled and self._ws._ws is not None` |
| `get_ws()` | `return self._ws`（永远返回对象） | `return self._ws if self._ws_enabled else None` |

## 5. CQ 码未 sanitize

### 现象
日志 `raw_message` 直接显示原始 CQ 码，如 `[CQ:forward,id=...]`。

### 根因
`stages.py` 的 `_log_via_styling` 把原始 `raw_data` 中的 `raw_message` 直接塞进 context，未经过 `sanitize` 处理。

### 修改内容
`core/pipeline/stages.py` 的 `_log_via_styling` 方法中，将 `raw_message` 入 context 前先调用 `sanitize()`：

```python
from core.gracy_adapter.onebot.sanitize import sanitize
raw_message = sanitize(raw_message)
```

## 7. Pipeline Stage 日志被 `[P50]` 污染

### 现象
SecurityFilter、BuiltinCommands、PluginHandler 三个 Stage 的每行日志都带 `[P50]`，如：

```
改前：[Core] - INFO - [Security] [P50] - 审计日志 ...
改后：[Core] - INFO - [Security] - 审计日志 ...
```

### 根因
`core/pipeline/stages.py` 中 3 个 Stage 的 `process()` 方法错误地添加了 `@log_attrs(priority="P50")` 装饰器。该装饰器本意是为**插件命令处理器**标注优先级（如 `/help` → P50），但 Pipeline Stage 是固定的顺序执行流程，不存在优先级概念。

此外 `build_attrs()` 在 `log_tool.py` 中的实现是：优先读取 LogRecord extra 属性，没有时才读上下文 `_log_attrs_ctx`。而 `@log_attrs` 把属性注入到上下文，结果上下文一直生效，所有框架日志都带上了 `[P50]`。

### 修改内容

#### `core/pipeline/stages.py`

| 项 | 改前 | 改后 |
|------|------|------|
| SecurityFilter.process | `@log_attrs(priority="P50")` | 删除 |
| BuiltinCommands.process | `@log_attrs(priority="P50")` | 删除 |
| PluginHandler.process | `@log_attrs(priority="P50")` | 删除 |
| import | `from core.decorators.logger import log_attrs` | 删除 |

但插件 handler 执行期间仍应显示优先级。改为：

- `CommandMatcher` 匹配 TOML 插件时，将 priority 存入 `ctx.extra["priority"]`
- `PluginHandler` 执行 handler 前，从 `ctx.extra["priority"]` 读取值，通过 `_log_attrs_ctx.set()` **仅在 handler 执行期间**注入日志上下文，用 `try/finally` 确保清理

```python
# PluginHandler.process 新增逻辑
priority = ctx.extra.get("priority")
_log_token = None
if priority is not None:
    _log_token = _log_attrs_ctx.set({"priority": f"P{priority}"})
try:
    await handler_func(ctx)
finally:
    if _log_token is not None:
        _log_attrs_ctx.reset(_log_token)
```

追加 import：
```python
import contextvars
from core.decorators.logger import _log_attrs_ctx
```

## 8. CLI `stop/restart` 按端口查进程不可靠

### 现象
执行 `gracy restart` 时：
1. 旧进程未被杀死，输出 "没有找到运行中的 GracyBot"
2. 新进程因端口被占启动失败，输出 `❌ 启动失败: ... returned non-zero exit status 1`
3. 旧进程继续运行，新旧冲突

### 根因
`core/tools/cli/system.py` 的 `stop_bot_process()` Windows 分支用 `netstat -ano | findstr ":{port} "` 查找进程。`netstat` 输出格式在不同系统/语言环境下有差异，`findstr` 格式可能匹配不上，且端口被僵死进程占用时无法识别。

### 修改内容

#### `core/tools/cli/system.py` — `stop_bot_process()`

**v1.9.56 第一次修正：** 用 `wmic` 替代 `netstat`

| 项 | 改前 | 改后 |
|------|------|------|
| 查找方式 | `netstat -ano \| findstr ":{port} "` 遍历 3 个端口 | `wmic process where "name='python.exe'" get processid,commandline /format:csv` |
| 匹配逻辑 | 按端口号匹配 | 命令行包含 `bot.py` 或 `gracy` |
| 自身排除 | ❌ 无 | ✅ `os.getpid()` 跳过 CLI 自身进程 |
| CSV 解析 | — | `rsplit(",", 1)` 从行尾取 PID |

**v1.9.57 第二次修正：** `wmic` 截断命令行，改用 PowerShell `Get-CimInstance`

| 项 | 改前 | 改后 |
|------|------|------|
| 查询方式 | `wmic ... get processid,commandline /format:csv`（CSV 格式，命令行截断 255 字符） | PowerShell `Get-CimInstance -Query "SELECT ..."`（WMI 对象，无截断） |
| 匹配精度 | `"bot.py" in line or "gracy" in line.lower()`（`gracy restart` 自身也被匹配） | `$_.CommandLine -match 'bot\.py'`（只精确匹配 bot.py，不含 CLI） |
| 自身排除 | `if pid == current_pid`（仅跳过当前 PID） | `$_.ProcessId -ne {current_pid}`（PowerShell 侧过滤，减少 Python 循环） |
| 兼容性 | `wmic` 已弃用，部分系统不可用 | `Get-CimInstance` PowerShell 5.1+ 原生支持 |
